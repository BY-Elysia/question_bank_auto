# 应用内 Skill 包

每个目录是一项模型能力的完整定义，业务工作流按任务类型选择 Skill，不把所有指令同时发给模型。

```text
question-extract/
├── SKILL.md             # 模型任务指令：使用时机、步骤、输出与失败边界
├── definition.json      # 程序调度：ID、版本、模型角色、工具允许列表、预算
├── skill.interface.ts   # TypeScript 执行接口
└── contracts/           # 输入输出类型及 JSON Schema 片段
```

SKILL.md 是行为契约，definition.json 是机器可读调度契约，二者共同组成同一版本的 Skill。请求与输出字段以 contracts 中的 schema 为准，执行权限以任务计划和服务端校验为准。修改行为指令也必须纳入版本管理；已运行任务应保留原指令版本，不能静默切换。

## 后续执行器加载约定（尚未实现）

1. 从服务端注册表按任务冻结计划中的 Skill ID 与版本定位包，不接受用户提供的任意文件路径。
2. 读取选中包的 definition.json 与 SKILL.md，核对名称、版本及所需模型能力。缺失文件应在执行前报错，不能悄悄退化成无指令调用。
3. 加载 SKILL.md 正文作为该步骤的可信任务指令，单独传入经过 schema 验证的用户输入。Markdown 链接仅供开发者阅读；执行器应显式提供解析后的输出 schema，而非依赖模型访问链接。
4. 对视觉任务先按租户权限解析资产并附加图像；资产 ID 本身不等于模型已看到图片。运行时服务承担这项确定性工作，不为无工具 Skill 自动开放读文件权限。
5. 将 Skill 允许列表与任务允许工具取交集，在服务端强制限制工具调用与预算。API 密钥由模型网关持有，不写入 SKILL.md。
6. 解析并校验输出，再交给工作流生成候选修改或产物；Skill 不直接提交文档。记录所用 Skill 版本及指令内容摘要以支持审计。

## 本轮范围

10 个 SKILL.md 定义行为与边界，状态仍为 planned。当前构建仅汇总协议和类型，不打包 Markdown；实现执行器时须同时完成指令资源打包、版本锁定和加载验证。现有 HTTP 接口仍返回 501。

这是题库后端自己的 Skill 包约定，不表示已安装为 Codex Skill，也不代表外部模型供应商会自动识别或加载这些文件。
